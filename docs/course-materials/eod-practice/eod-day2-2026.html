Yesterday we ran a complete workflow on the Toolik dataset using one column of it. Today you will write a data biography of the whole thing: where it came from, what it covers, what condition it is in, and what somebody needs to know before trusting a number computed from it.

What is a data biography?

A data biography is a short written account of a dataset: where it came from, what it covers, what condition it’s in, and what a reader needs to know before trusting anything computed from it. Working data scientists write them constantly, usually in the first cells of a notebook, because the alternative is finding the problem after you’ve built a whole analysis on top of it (which is a much worse day!).

Your deliverable today is a biography of the Toolik weather data, written in your notebook as markdown, with code cells showing the evidence for every claim you make.

Evidence is the important part: every statement in your biography must be backed by a cell that produced it. Not “the data covers about thirty years,” but “the data covers 1988 to 2018,” with the cell that told you so sitting right above it.

Setup

  1. Create a new notebook named EOD_Day2_Data_Biography.ipynb.

  2. Add a title cell:

# Day 2 EOD: A Data Biography of Toolik Field Station Weather

Date: 09/01/2026
  1. Import pandas and read the data:
The file is at:
https://eds-217-essential-python.github.io/data/toolik_weather.csv
About this station

Toolik Field Station sits on the North Slope of Alaska, above the Arctic Circle, and is part of the Arctic Long Term Ecological Research (LTER) network. It has been collecting daily weather since the late 1980s. Keep the location in mind while you work. Some of the numbers you find should look reasonable for an Arctic site, and some of them should look suspicious!

Part 1: Vital statistics

Answer each question below with code, then write the answer in a markdown cell beneath it.

  1. How many rows and how many columns does the dataset have?
  2. What are the column names? Get them as a Python list.
  3. What is the data type of each column?
  4. What years does the record cover? (You can read the earliest and latest year off .describe().)
Something to notice

Look closely at the Date column’s data type. Does it match what you’d expect a date to be? Say what pandas has actually stored there. You don’t need to fix it, and we’ll handle dates properly on Day 6.

Part 2: The health check

  1. Run .info(). How many columns have fewer non-null values than there are rows?
  2. Use .isnull().sum() to count missing values per column. Which three columns are the emptiest?
  3. One of the flag columns has a value in only a handful of rows, and is empty everywhere else. Which one, and how many values does it actually have?
Interpret, don’t just report

A column that is 99% empty is not necessarily broken. Think about what a “flag” column is for in an environmental dataset, and write a sentence explaining why it might be mostly empty by design. Reading a table tells you that the column is empty. Understanding the dataset tells you whether being empty is a problem.

Part 3: What varies, and what doesn’t

  1. Use .value_counts() on LTER_Site and on Station. What do you learn? Does either column tell you anything?
  2. Use .value_counts() on Flag_Daily_AirTemp_Mean_C. What values appear, and what do you think they mean?
  3. Use .value_counts() on the Year column and look at both ends of the result, with .head() and then with .tail(). Do all years have the same number of observations? What would explain a year with fewer?

Part 4: The numbers

  1. What is the mean daily air temperature across the whole record? The minimum? The maximum?
  2. Are the mean, the minimum and the maximum plausible for a site above the Arctic Circle? Say why or why not.
  3. Pick one other numeric column and report its range. Does anything about it look wrong?
Remember Session 2B

.describe() will average anything you point it at. Before you report a mean, satisfy yourself that the column holds one kind of thing, measured one way.

Part 5: A tidier table

  1. Build a list of the five columns you’d keep if you had to hand this dataset to a colleague who only cared about temperature. Use it to make a smaller DataFrame.
  2. Build a dictionary that renames at least two of those columns to something shorter and clearer. Apply it with .rename(columns=...) and confirm the new names.

Part 6: Write the biography

In a single markdown cell, write 200 to 300 words covering:

  • What this dataset is. Source, station, what is measured, at what frequency.
  • Coverage. How many rows, what time span, how many variables.
  • Condition. What’s missing and where. Which columns you would and would not trust.
  • Cautions. Two specific things a person using this data should know before computing anything from it.
  • Fitness for purpose. Could you use this dataset to describe how Arctic summer temperatures have changed since 1988? Say yes or no, and say what would need checking first.

Write it for a colleague who has never opened the file. No bullet fragments; complete sentences.

🧭 Field Note: looping over your column list

If you’d like to check several columns at once rather than one at a time, you can loop over a list. We cover loops properly in this afternoon’s live-coding session, so here is the whole pattern. Adapt the list, don’t write the loop from scratch:

for column_name in ['Daily_AirTemp_Mean_C', 'Daily_Precip_Total_mm']:
    print(column_name, toolik[column_name].isnull().sum())

The loop is optional! Everything above can be done one column at a time.

Wrap-up

Before you close your notebook, check that:

  • every factual claim in your biography has a code cell above it that produced the evidence
  • your notebook reads top to bottom as a document, not as a pile of cells
  • you have used at least one list and at least one dictionary
  • you noticed at least one thing about this dataset that would have caused a problem if you hadn’t looked

The last check is the whole point of this practice, because a problem you catch now is a problem you never have to unpick out of a finished analysis.

If you get stuck, say what you tried and ask Cella or Kelly while you are still here. A small problem you have been staring at alone for twenty minutes usually turns out to be a small problem!
